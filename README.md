# 🌐 Event Booking

Система асинхронного бронирования билетов на базе микросервисной архитектуры.

## 🛠️ Технологический стек

* **Платформа**: .NET 10 / C# 12
* **Архитектура**: Clean Architecture, CQRS (MediatR), Microservices
* **Инфраструктура**: Apache Kafka (Confluent.Kafka), PostgreSQL (EF Core), Redis (StackExchange.Redis)
* **Контейнеризация**: Docker, Docker-Compose
* **Тестирование**: xUnit, FluentAssertions, Testcontainers

---

## ⚙️ Архитектура системы

Система разделена на три автономных микросервиса со своими изолированными базами данных. Зависимости направлены строго внутрь ядра: `Domain ← Application ← Infrastructure ← Api`.

* **🧩 Auth.Service** (`:5125`) — Регистрация, вход и выдача JWT-токенов.
* **🧩 Events.Service** (`:5130`) — Управление событиями (CRUD) и учёт доступных мест.
* **🧩 Bookings.Service** (`:5063`) — Создание, отмена и фоновая обработка заявок на бронь.

Общие контракты и интеграционные события вынесены в разделяемую библиотеку `src/Shared`.

## 🔄 Поток BookingConfirmed (Интеграция через Kafka)

Службы взаимодействуют асинхронно через брокер сообщений Apache Kafka (Топик: `booking-confirmed`). Контракт события `BookingConfirmedEvent` лежит в `src/Shared/Contracts`.

1. **Создание заявки**: Пользователь делает `POST /bookings/{eventId}`. Бронь сохраняется в БД со статусом `Pending`.
2. **Публикация**: Фоновый `BookingBackgroundService` забирает «висящие» брони, подтверждает их в локальной БД и вызывает `KafkaPublisher`. Сообщение отправляется в Kafka с ключом `EventId` для гарантии порядка обработки.
3. **Инициализация**: При старте сервиса **Events** компонент `KafkaTopicInitializer` автоматически проверяет и создает топик, если его нет.
4. **Потребление**: `BookingConfirmedConsumer` (группа `events-service-group`) читает сообщения, создает Scoped-контекст, вызывает бизнес-логику `TryReserveSeats` и уменьшает `AvailableSeats` в БД.

⚠️ **Бизнес-сценарии и крайние случаи:**
* **Овербукинг / Конфликт мест**: При попытке забронировать место сверх лимита система возвращает `409 Conflict`. Бронь не создается.
* **Ошибка в фоновом потоке**: Если при обработке события в Кафке выясняется, что мест нет или событие не найдено, ошибка явно логируется, а сообщение пропускается, чтобы консьюмер не заблокировал чтение очереди. Для корректной параллельной обработки используются `lock` и `SemaphoreSlim`.

## 🗄️ Стратегия кеширования (Events.Service)

Кеш внедрен для снижения нагрузки на PostgreSQL при выполнении частых публичных запросов на чтение: карточки конкретного события и виджета топ-10 популярных событий на главной странице.

### Что кешируется и почему

| Данные                        | Ключ           | Паттерн     | TTL        | Стратегия инвалидации             |
|-------------------------------|----------------|-------------|------------|-----------------------------------|
| Событие по идентификатору     | `event:{id}`   | Cache-Aside | 300 секунд | Активная (инвалидация при записи) |
| Топ-10 по доле проданных мест | `events:top10` | Cache-Aside | 60 секунд  | Пассивная (только по TTL)         |

> **Формула рейтинга:** Доля продаж рассчитывается как `(total_seats - available_seats) / total_seats`. Эндпоинт `GET /events/top` доступен без авторизации, поэтому кеширование защищает базу данных от высокой нагрузки при наплыве пользователей.

Для соблюдения принципов Clean Architecture слой `Application` изолирован от инфраструктуры и взаимодействует с кешем исключительно через кастомный интерфейс `ICacheService`. Его конкретная реализация на базе Redis (`StackExchange.Redis`) вынесена в слой `Infrastructure`. Внутренний Redis-клиент регистрируется как `Singleton`, позволяя эффективно переиспользовать TCP-соединения на протяжении всего жизненного цикла процесса.

### Настройка TTL (Time-To-Live)

* **Карточка события (5 минут):** Читается часто, но может изменяться администратором или при покупке билетов. Короткий TTL гарантирует актуализацию данных, даже если сквозная инвалидация даст сбой.
* **Топ-10 популярных событий (1 минута):** Рейтинговый агрегат. Временное отставание данных на главной странице не критично для бизнес-логики, а минутный TTL избавляет от необходимости дорогостоящего пересчета топа при каждом новом бронировании.

Параметры кеширования конфигурируются в секции `Redis` (`EventTtlSeconds`, `TopEventsTtlSeconds`) файла `appsettings.Development.json` и могут быть переопределены через переменные окружения (например, `Redis__ConnectionString`).

### Поведение при изменении данных

Для сохранения консистентности данных карточки события выбрана стратегия **активной инвалидации при записи (удаление ключа)**:

1. Изменения успешно транслируются и сохраняются в PostgreSQL.
2. Через метод `ICacheService` из Redis удаляется соответствующий ключ `event:{id}`.
3. Следующий запрос `GET /events/{id}` сталкивается с промахом кеша (Cache Miss), читает актуальное состояние из БД и заново «прогревает» кеш.

Этот подход исключает риск записи в Redis рассинхронизированного или «грязного» состояния. Инвалидация вызывается в трех случаях:
* При ручном обновлении события администратором (`PUT /events/{id}`).
* При удалении события (`DELETE /events/{id}`).
* Внутри `BookingConfirmedConsumer` при успешной обработке события из Kafka (так как уменьшается количество `AvailableSeats` и кеш карточки мгновенно устаревает).

Кеш топ-10 **не инвалидируется принудительно** и обновляется естественным образом раз в минуту по истечении TTL, что существенно экономит ресурсы сервера.

### 🛡️ Отказоустойчивость

При конфигурации клиента установлен флаг `AbortOnConnectFail = false`. Внутри реализации `ICacheService` все исключения Redis (ошибки Get/Set/Remove) перехватываются, логируются и «гасятся», не прерывая выполнение основного потока приложения.

Если инстанс Redis недоступен, микросервис продолжает стабильно функционировать, перенаправляя все запросы напрямую в PostgreSQL (работа в режиме постоянного Cache Miss без генерации ошибок 500 для клиентов).

## 📊 Наблюдаемость и мониторинг

В систему интеграции микросервисов внедрен полноценный стек Observability (наблюдаемости) для сбора логов, метрик и распределенных трассировок.

### Инструменты и технологии
*   **OpenTelemetry SDK** — интегрирован во все микросервисы для автоматического сбора телеметрии входящих/исходящих HTTP-запросов и SQL-операций через Entity Framework Core.
*   **Serilog** — настроен в качестве единого провайдера логирования для вывода структурированных логов в формате JSON (`CompactJsonFormatter`).
*   **Jaeger** — используется как централизованное хранилище и UI для распределенной трассировки (работает по Push-модели напрямую через протокол OTLP). Адрес приёмника задаётся `Otlp:Endpoint`: локально это `http://localhost:4317`, в Docker Compose его перекрывает переменная `Otlp__Endpoint=http://jaeger:4317`.
*   **Prometheus** — выполняет сбор (Scraping) метрик рантайма .NET и ASP.NET Core с каждого сервиса по Pull-модели через эндпоинты `/metrics`.
*   **Grafana** — инструмент визуализации со встроенным дашбордом для отслеживания Latency, Throughput и Error Rate.

### Как запустить стек мониторинга

Стек разворачивается автоматически вместе с основной инфраструктурой проекта с помощью Docker Compose:

```bash
cd devops
docker compose up -d
```

В Docker-сети поднимаются и настраиваются новые контейнеры:
*   `eventapi-prometheus` — сборщик метрик.
*   `eventapi-jaeger` — приемник OTLP-трейсов и визуализатор цепочек вызовов.
*   `eventapi-grafana` — аналитическая панель графиков.

### Провизионинг Grafana

Дашборды и источник данных не создаются вручную в UI. Grafana при старте читает каталог `/etc/grafana/provisioning` и сама поднимает конфигурацию из репозитория. В `docker-compose.yml` этот каталог смонтирован из `devops/grafana/provisioning` (только чтение).

Механизм из двух частей:

1. **Datasource.** Файл `devops/grafana/provisioning/datasources/datasource.yml` регистрирует Prometheus (`http://prometheus:9090`) как источник по умолчанию. У него зафиксирован `uid: prometheus`: на этот идентификатор ссылаются панели в JSON-дашбордах. Источник помечен `editable: false`, поэтому его нельзя переопределить из интерфейса.
2. **Дашборды.** Файл `devops/grafana/provisioning/dashboards/dashboards.yml` описывает файловый провайдер. Каждые 30 секунд Grafana сканирует `/var/lib/grafana/dashboards` (смонтирован из `devops/grafana/dashboards`) и загружает JSON-файлы в папку **Event Booking**. Правка дашборда в репозитории подхватывается без импорта через UI: достаточно дождаться следующего сканирования или перезапустить контейнер Grafana.

JSON в `devops/grafana/dashboards` — это экспорт Grafana: у каждой панели в `datasource.uid` зашито значение `prometheus`. Оно должно совпадать с `uid` в `datasource.yml`. Если поменять uid только в provisioning, панели перестанут находить источник данных.

### ❌ Обработка ошибок

В случае ошибок API возвращает ответы в стандартном формате **Problem Details (RFC 7807)**:

```json
{
  "type": "https://ietf.org",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00",
  "errors": {
    "Title": ["Наименование события обязательно для заполнения."]
  }
}
```
