# 🌐 Event Booking

Система асинхронного бронирования билетов на базе микросервисной архитектуры.

## 🛠️ Технологический стек

* **Платформа**: .NET 10 / C# 12
* **Архитектура**: Clean Architecture, CQRS (MediatR), Microservices
* **Инфраструктура**: Apache Kafka (Confluent.Kafka), PostgreSQL (EF Core)
* **Контейнеризация**: Docker, Docker-Compose
* **Тестирование**: xUnit, FluentAssertions, Testcontainers

---

## ⚙️ Архитектура системы

Система разделена на три автономных микросервиса со своими изолированными базами данных. Зависимости направлены строго внутрь ядра: `Domain ← Application ← Infrastructure ← Api`.

* **🧩 Auth.Service** (`:5125`) — Регистрация, вход и выдача JWT-токенов.
* **🧩 Events.Service** (`:5130`) — Управление событиями (CRUD) и учёт доступных мест.
* **🧩 Bookings.Service** (`:5063`) — Создание, отмена и фоновая обработка заявок на бронь.

Общие контракты и интеграционные события вынесены в разделяемую библиотеку `src/Shared`.

## 🔄 Поток BookingConfirmed (Интеграция через Kafka)

Службы взаимодействуют асинхронно через брокер сообщений Apache Kafka (Топик: `booking-confirmed`). Контракт события `BookingConfirmedEvent` лежит в `src/Shared/Contracts`.

1. **Создание заявки**: Пользователь делает `POST /bookings/{eventId}`. Бронь сохраняется в БД со статусом `Pending`.
2. **Публикация**: Фоновый `BookingBackgroundService` забирает «висящие» брони, подтверждает их в локальной БД и вызывает `KafkaPublisher`. Сообщение отправляется в Kafka с ключом `EventId` для гарантии порядка обработки.
3. **Инициализация**: При старте сервиса **Events** компонент `KafkaTopicInitializer` автоматически проверяет и создает топик, если его нет.
4. **Потребление**: `BookingConfirmedConsumer` (группа `events-service-group`) читает сообщения, создает Scoped-контекст, вызывает бизнес-логику `TryReserveSeats` и уменьшает `AvailableSeats` в БД.

⚠️ **Бизнес-сценарии и крайние случаи:**
* **Овербукинг / Конфликт мест**: При попытке забронировать место сверх лимита система возвращает `409 Conflict`. Бронь не создается.
* **Ошибка в фоновом потоке**: Если при обработке события в Кафке выясняется, что мест нет или событие не найдено, ошибка явно логируется, а сообщение пропускается, чтобы консьюмер не заблокировал чтение очереди. Для корректной параллельной обработки используются `lock` и `SemaphoreSlim`.

#### 1. Шаг: Запуск инфраструктуры (Docker)
```bash
cd devops
docker compose up -d
```
*Убедитесь, что контейнеры базы и Кафки перешли в статус healthy.*

#### 2. Шаг: Запуск микросервисов (локально)
Запустите три терминала из корня репозитория:
```bash
dotnet run --project src/Auth.Service/Auth.Api/Auth.Api.csproj
dotnet run --project src/Events.Service/Events.Api/Events.Api.csproj
dotnet run --project src/Bookings.Service/Bookings.Api/Bookings.Api.csproj
```

#### 🔒 Аутентификация в Swagger:
1. Перейдите в Auth: `http://localhost:5125/swagger` и выполните `POST /auth/login`.
2. Скопируйте токет из ответа.
3. В нужном Swagger-интерфейсе нажмите **Authorize** ➡️ введите `Bearer <ваш_токен>` ➡️ **Authorize**.
   *JWT-секрет настраивается через `Jwt:SecretKey` в `appsettings.Development.json`.*

### 🔄 Миграции базы данных
Миграции применяются автоматически при старте каждого API. Для генерации новой миграции:
```bash
dotnet ef migrations add <Имя> --project src/Auth.Service/Auth.Infrastructure --startup-project src/Auth.Service/Auth.Api
dotnet ef migrations add <Имя> --project src/Events.Service/Events.Infrastructure --startup-project src/Events.Service/Events.Api
dotnet ef migrations add <Имя> --project src/Bookings.Service/Bookings.Infrastructure --startup-project src/Bookings.Service/Bookings.Api
```

## 📖 Документация API

### 📍 API Эндпоинты

#### Auth (`:5125`)
* `POST /auth/register` — Регистрация нового пользователя (Коды: 204, 400, 409)
* `POST /auth/login` — Аутентификация и выдача JWT (Коды: 200, 400, 401)
* `GET /users/{id}` — Получить профиль пользователя (Коды: 200, 401, 403, 404)
* `PUT /users/password` — Сменить пароль текущего пользователя (Коды: 204, 400, 401)

#### Events (`:5130`)
* `GET /events` — Получить список событий с пагинацией и фильтрацией (Коды: 200, 401)
* `GET /events/{id}` — Получить событие по ID (Коды: 200, 401, 404)
* `POST /events` — Создать новое событие `[Admin]` (Коды: 201, 400, 401, 403)
* `PUT /events/{id}` — Редактировать событие `[Admin]` (Коды: 204, 400, 401, 403, 404)
* `DELETE /events/{id}` — Удалить событие `[Admin]` (Коды: 200, 401, 403, 404)

### ❌ Обработка ошибок

В случае ошибок API возвращает ответы в стандартном формате **Problem Details (RFC 7807)**:

```json
{
  "type": "https://ietf.org",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00",
  "errors": {
    "Title": ["Наименование события обязательно для заполнения."]
  }
}
```

<details>
<summary>📋 Посмотреть расшифровку HTTP-кодов ответов при ошибках</summary>

| Код                  | Причина                               | Пример сценария                                                  |
|:---------------------|:--------------------------------------|:-----------------------------------------------------------------|
| `400 Bad Request`    | Ошибка валидации параметров.          | Не передан обязательный параметр.                                |
| `401 Unauthorized`   | Не аутентифицирован.                  | Пользователь пытается забронировать событие без входа в систему. |
| `403 Forbidden`      | Доступ запрещен.                      | Пользователь пытается отменить чужое бронирование.               |
| `404 Not Found`      | Ресурс не найден.                     | Запрос несуществующего события.                                  |
| `409 Conflict`       | Отсутствие доступных мест на событии. | Попытка забронировать места при отсутствии доступных.            |
| `500 Internal Error` | Внутренняя ошибка сервера.            | Непредвиденный сбой в базе данных или коде.                      |

</details>
